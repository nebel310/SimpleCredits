# Проверка скоринговой модели на реалистичных данных

Проверка выполнялась на `scorecard-linear-v1` (логистический скоркард, 207 признаков). Сейчас в проде `catboost-v2`, поэтому таблицы ниже — исторические и не описывают текущие решения. Заявки отправлялись через `POST /scoring/batch` — без сохранения в базу. Скрипт и все профили — `frontend/scripts/model-check.py`, перезапуск:

```bash
cd backend && uv run python ../frontend/scripts/model-check.py
```

## Модель настоящая, просто быстрая

Решение считает обученная модель в контейнере `ml` по gRPC: у разных данных разный балл, PD и грейд, версия и метрики видны в `GET /scoring/model-info`. Актуальная модель — `catboost-v2`, ROC-AUC на тесте 0,787, Gini 0,574 (у исторической scorecard было 0,857 и 0,714). Заявка обрабатывается за доли секунды, потому что:

- модель лёгкая и считает 207 признаков за миллисекунды;
- при создании заявки бэкенд берёт данные ЕГРЮЛ/ФНС/БКИ напрямую из генераторов (`services/enrichment.py`), без искусственной задержки 0,3–1,5 с, которая есть у HTTP-эндпоинтов `/mock/*`.

## Как модель решает

1. Правила политики (`ml/.../scoring/policy.py`) идут первыми: текущая просрочка или просрочка 60+ дней за год → отказ при любом PD.
2. PD ≥ 35% → отказ, 20–35% → ручная проверка (серая зона).
3. Платежи по долгам > 55% месячной выручки → ручная проверка.
4. Сумма > 60% годовой выручки и > 3 млн → одобрение с условием снизить сумму до 50% выручки.
5. Иначе одобрение.

Грейд считается только по PD: A < 2%, B < 5%, C < 10%, D < 20%, E — 20% и выше.

## Чувствительность: меняем один фактор у хорошей компании

Направление влияния правильное у всех факторов: хуже показатель — выше PD.

| Фактор | От → до | PD |
|---|---|---|
| Просрочка за год | 0 → 90 дней | 1,3% → 3,1% (с 60 дней — отказ по правилу) |
| Загрузка лимитов | 0 → 95% | 1,0% → 2,6% |
| Платежи по долгам в месяц | 0 → 6 млн (при выручке 10 млн/мес) | 1,3% → 8,1% (ручная проверка) |
| Заявок за 6 месяцев | 0 → 10 | 1,3% → 4,8% |
| Общий долг | 0 → 150 млн | 1,3% → 5,2% |
| Возраст бизнеса | 20 лет → 5 месяцев | 0,8% → 2,3% |
| Сотрудников | 1000 → 1 | 0,02% → 1,8% |
| **Чистая прибыль** | **+18 млн → −20 млн** | **1,3% → 1,7%** |

## Что передать команде ML и бэкенда

Это исторические наблюдения времён `scorecard-linear-v1`; после перехода на CatBoost часть выводов неактуальна.

1. **Убыток почти не влияет на решение.** Компания с убытком 20 млн при выручке 120 млн остаётся в грейде A.
2. **Отсутствие кредитной истории выглядит как плюс.** Бизнес 1,5 года без кредитов, который просит 42% годовой выручки, получает PD 0,4% — лучше, чем у зрелых компаний.
3. **Признаков соцсетей, сайта и отзывов на картах нет в запросе.** `social_followers`, `website_visits`, `geo_reviews_count` не передаются из бэкенда, модель подставляет значения по умолчанию. У всех заявок одинаковые вклады: `social_followers` — главный фактор риска (+0,95), остальные — «снижают риск». Описание у них общее («Фактор повышает риск»). Фронтенд показывает их понятным названием и пометкой «в заявке таких данных нет».
4. **Балл и грейд читаются по-разному.** Балл 772 из 1000 — это грейд E (PD 22,8%). Пользователю это непривычно, фронтенд показывает оба числа рядом с подписью уровня риска.
5. **После перезапуска ML бэкенд до ~2 минут отвечает 502.** gRPC-канал создаётся один раз при старте и переподключается с нарастающей паузой. В `docker compose` это не мешает (бэкенд стартует после healthy ML), но если ML упадёт и поднимется, заявки какое-то время будут получать «Ошибка обработки».
