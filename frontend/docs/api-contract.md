# Как фронтенд работает с API бэкенда

Источник правды — `backend/webdoc.yaml`, `backend/README.md` и `USERFLOW.md`. Типы фронтенда (`src/api/types.ts`) повторяют Pydantic-схемы бэкенда без переименований. Все вызовы собраны в `src/api/index.ts`.

## Общее

- Базовый адрес — `VITE_API_URL` (по умолчанию `/api`). В разработке его проксирует Vite, в Docker — nginx: `/api/x` → `http://backend:3001/x`.
- Защищённые запросы идут с `Authorization: Bearer <access_token>`.
- Ошибка бэкенда `{"detail": "..."}` показывается пользователю как есть. Ошибки валидации FastAPI (422, `detail` — массив) превращаются в «Проверьте поля: …». Тело ответа сохраняется в `ApiError.data` — например, `application_id` сохранённой заявки при сбое ML.
- 401 → `POST /auth/refresh` с `{"refresh_token": "…"}` в теле (не в адресе — адреса попадают в логи) → запрос повторяется один раз. Для демо-аккаунта, если refresh не сработал, фронтенд входит заново тем же логином. Иначе — выход на экран входа.
- Сессия хранится в `sessionStorage`: в разных вкладках можно войти под разными аккаунтами.

## Эндпоинты

| Метод | Путь | Где используется |
|---|---|---|
| POST | `/auth/register` | Регистрация, первый вход демо-аккаунта |
| POST | `/auth/login` | Вход, демо-вход, вход администратора |
| POST | `/auth/refresh` | Продление сессии при 401 |
| POST | `/auth/logout` | Кнопка «выйти» в шапке |
| GET | `/auth/me` | После входа |
| PATCH | `/auth/me` | Профиль компании; демо-профиль при первом входе |
| GET | `/products` | Каталог, форма заявки, названия продуктов |
| POST | `/applications` | Новая заявка с заголовком `Idempotency-Key`. Ответ 201 уже содержит итоговый статус |
| GET | `/applications` | Главная и «Мои заявки» (все страницы, новые сверху) |
| GET | `/applications/{id}` | Карточка заявки |
| GET | `/applications/{id}/events` | История заявки и трекер этапов |
| POST | `/applications/{id}/accept` | «Принять предложение» |
| POST | `/applications/{id}/issue` | «Подтвердить и оформить» — модельная выдача, номер договора |
| POST | `/applications/{id}/reject` | «Отказаться» от предложения |
| POST | `/applications/{id}/retry` | «Повторить проверку» после сбоя |
| GET | `/admin/applications` | Кабинет банка: все заявки |
| POST | `/admin/applications/{id}/decision` | Кабинет банка: решение по заявке на ручной проверке |
| GET | `/admin/stats/overview` | Кабинет банка: статистика |
| GET | `/scoring/model-info` | Кабинет банка: версия и метрики модели |
| GET | `/mock/egrul/{inn}` | Профиль: «Найти в ЕГРЮЛ» — подставить реквизиты |
| GET | `/mock/fns/{inn}` | Профиль: справка ФНС рядом с реквизитами |
| GET | `/mock/bki/{inn}` | Профиль: кредитная история из БКИ (подтягивается после поиска в ЕГРЮЛ, только для чтения) |
| WS | `/ws/applications?token=…` | Живые обновления статуса и событий |

Не используются: `/auth/users`, `/files/*`, `/scoring/batch`, `/products/{code}` — в пути пользователя по USERFLOW они не нужны.

## Создание заявки

```json
POST /applications
{ "product_type": "term_loan" | null, "requested_amount_rub": 3000000, "term_months": 12, "purpose": "working_capital", "segment": "small" }
```

- `product_type: null` — пользователь выбрал «Подобрать за меня». Что подберёт банк, фронтенд показывает заранее по тем же правилам (`src/lib/rules.ts`).
- `segment` фронтенд считает по профилю (до 15 сотрудников и до 120 млн ₽ выручки — микробизнес); бэкенд всё равно определяет его сам.
- `Idempotency-Key` — один на попытку: двойное нажатие и повтор сети вернут ту же заявку. При изменении параметров ключ меняется.
- Профиль должен быть заполнен (иначе 400 «Профиль компании не заполнен…») — фронтенд сначала отправляет на `#/profile`.
- 422 со строкой в `detail` — выбранный продукт не подходит (сегмент, форма, возраст, сумма, срок). Фронтенд проверяет это до отправки.
- 502/504 с `application_id` — ML недоступен, заявка сохранена со статусом `failed`: фронтенд открывает её карточку с кнопкой «Повторить проверку».
- Пока запрос идёт, этапы на экране двигаются по событиям WebSocket (`enriched`, `status_changed`).

## Статус → что видит пользователь

Подпись, баннер и следующее действие собирает `display()` в `src/lib/labels.ts`. Кнопки клиента — из поля `actions`, которое присылает бэкенд.

| `status` | `outcome` | Заголовок | Кнопки (`actions`) |
|---|---|---|---|
| `pending` | — | Заявка обрабатывается (фронтенд дополнительно опрашивает заявку раз в 2 с) | — |
| `confirmed` | — | Заявка одобрена | принять, отказаться |
| `different` | `ALTERNATIVE_PRODUCT`, сумма как в заявке, продукт выбрал банк | Подобрали продукт | принять, отказаться |
| `different` | `ALTERNATIVE_PRODUCT` | Подобрали другой продукт | принять, отказаться |
| `different` | `COUNTER_OFFER` | Предлагаем другие условия (предложенная и запрошенная сумма) | принять, отказаться |
| `different` | `MANUAL_REVIEW` | Нужна дополнительная проверка — не оффер | — |
| `declined` | — | Банк отказал + причина (или «Нет подходящего продукта» при `NO_SUITABLE_PRODUCT`) | — |
| `failed` | — | Проверка не завершилась | повторить |
| `accepted` | — | Предложение принято | оформить, отказаться |
| `issued` | — | Кредит оформлен, номер договора | — |
| `rejected_by_client` | — | Вы отказались от предложения | — |

Что видит клиент и что — банк:

- клиент — категорию риска (низкий / средний / высокий), главные причины решения, до 5 факторов, посчитанных по данным заявки, и советы «что делать дальше» (шаблоны по кодам причин и факторам риска);
- банк — балл, PD, грейд, решение модели с кодами, все факторы модели, включая признаки, которых нет в заявке (с пометкой), и форму решения по ручной проверке.

Коды причин (`CURRENT_PAST_DUE`, `HIGH_RISK_SCORE`, `RISK_IN_GREY_ZONE`, `NO_SUITABLE_PRODUCT` и др.) переводятся в `src/lib/labels.ts`.

## WebSocket

Одно соединение на вкладку, пока пользователь вошёл. При закрытии — переподключение через 1–5 с; при коде `4401` — продление сессии и переподключение с новым токеном. После переподключения экраны перечитывают заявку и `/events` (USERFLOW §8). В `status_changed` бэкенд шлёт клиенту только тип результата, объяснение и доступные действия — без балла и PD. Администратору бэкенд события чужих заявок не шлёт, поэтому кабинет банка обновляется раз в 15 секунд.
