# USERFLOW.md

## 1. Что это за продукт

Веб-платформа умного кредитного кабинета для малого и микробизнеса. Предприниматель заходит на сайт, выбирает сумму и (опционально) кредитный продукт, заполняет данные о себе и компании, отправляет заявку. Бэкенд обогащает данные через моковые государственные сервисы, отправляет их в ML-сервис скоринга, получает решение и присваивает заявке финальный статус. Пользователь видит результат в реальном времени через WebSocket.

Финальная точка пути — **синтетическая выдача кредита**: клиент принимает предложение банка, подтверждает условия и получает номер модельного договора (статус `issued`). Реальных денежных проводок и документооборота нет. Сопровождение кредита после выдачи в MVP не реализуется.

## 2. Роли

| Роль | Что делает |
|---|---|
| `user` | Регистрируется, заполняет профиль компании, создаёт и просматривает свои заявки |
| `admin` | Просматривает все заявки и статистику, принимает решение по заявкам на ручной проверке |

Других ролей нет. Пользователь и компания — одна сущность: у каждого `user` в профиле есть реквизиты его компании и финансовые показатели.

## 3. Основные сущности

### UserOrm

Пользователь + компания + актуальные финансовые данные.

**Базовые поля:**
- `id`, `username`, `email`, `hashed_password`, `role` (`user` / `admin`)
- `avatar_id`, `bio`, `birth_date`, `gender`
- `created_at`

**Поля компании:**
- `inn`, `ogrn`, `legal_name`, `legal_form`, `okved`, `region`, `registration_date`, `employee_count`

**Поля финансов (последние известные):**
- `annual_revenue_rub`, `annual_net_profit_rub`, `ebitda_rub`, `total_debt_rub`, `monthly_revenue_rub`, `monthly_expenses_rub`, `accounts_receivable_rub`, `cash_balance_rub`, `period_end`

**Поля кредитной истории (последние известные):**
- `active_obligations_count`, `total_outstanding_rub`, `monthly_debt_payments_rub`, `max_days_past_due_12m`, `has_current_past_due`, `credit_utilization`, `closed_obligations_count`, `applications_last_6m`

Профиль заполняется при регистрации или при первом создании заявки. Обновляется через `PATCH /auth/me`.

### ProductOrm

Каталог кредитных продуктов. См. раздел 4.

### ApplicationOrm

Кредитная заявка. Один пользователь — много заявок. Заявка хранит снимок всех данных компании и финансов на момент подачи, чтобы результат был воспроизводим.

**Поля:**
- `id`, `application_id` (uuid, публичный), `user_id`
- `status` — см. раздел 5
- `product_type` — `microloan` / `term_loan` / `overdraft` / `credit_line` / `leasing` / `null` (null — банку не подошёл ни один продукт)
- `product_selected_by_system` — true, если продукт подобрал банк (клиент не выбирал)
- `outcome` — уточнение статуса `different`: `ALTERNATIVE_PRODUCT` / `COUNTER_OFFER` / `MANUAL_REVIEW`
- `offer` (JSONB) — условия предложения: продукт, сумма, срок, ставка, платёж, общая сумма, переплата
- `contract_number`, `issued_at` — номер модельного договора и момент синтетической выдачи
- `bank_decision` (JSONB) — решение сотрудника банка по ручной проверке: решение, комментарий, кто и когда
- `idempotency_key` — ключ из заголовка `Idempotency-Key` (уникален в пределах пользователя)
- `requested_amount_rub`, `term_months`, `purpose`, `segment`
- Snapshot полей компании (inn, ogrn, legal_name, legal_form, okved, region, registration_date, employee_count)
- Snapshot полей финансов (8 полей)
- Snapshot полей кредитной истории (8 полей)
- `enriched_data` (JSONB) — что вернули мок-госуслуги
- `scoring_result` (JSONB) — полный ответ ML-сервиса (score, pd, risk_grade, reason_codes, decision, conditions, model_version)
- `explanation` (TEXT) — понятное объяснение для клиента: шаблон по кодам причин или комментарий сотрудника банка
- `created_at`, `updated_at`, `submitted_at`

### ApplicationEventOrm

История событий по заявке. Пишется автоматически, читается для отображения таймлайна и для восстановления состояния после переподключения к WebSocket.

**Поля:**
- `id`, `application_id`, `event_type`, `payload` (JSONB), `created_at`

Типы событий: `created`, `enriched`, `scored`, `status_changed`, `failed`, `retry_started`, `offer_accepted`, `issued`, `offer_rejected`, `bank_decision`.

Новые колонки в существующие таблицы добавляются при старте бэкенда (`database.add_missing_columns`), поэтому база из прошлой версии обновляется без потери данных.

## 5. Статусы заявки

| Статус | Когда присваивается |
|---|---|
| `pending` | Заявка создана (или запущен повтор проверки), ждём ответа ML |
| `failed` | Техническая ошибка: ML недоступен, таймаут. Заявку можно повторить (`POST /applications/{id}/retry`) |
| `confirmed` | ML вернул `approve` **и** клиент сам выбрал продукт, и продукт подошёл |
| `different` | ML вернул `approve_with_conditions` / `manual_review` **или** продукт подобрал банк |
| `declined` | ML вернул `decline`, банк отказал по ручной проверке или не подошёл ни один продукт (`NO_SUITABLE_PRODUCT`) |
| `accepted` | Клиент принял предложение |
| `issued` | Клиент подтвердил условия — кредит оформлен и (синтетически) выдан |
| `rejected_by_client` | Клиент отказался от предложения |

**Правила маппинга `decision` → `status`:**

```
approve + продукт выбрал клиент     → confirmed
approve + продукт подобрал банк     → different (ALTERNATIVE_PRODUCT)
approve_with_conditions             → different (COUNTER_OFFER или ALTERNATIVE_PRODUCT)
manual_review                       → different (MANUAL_REVIEW)
decline                             → declined
ошибка ML / сети                    → failed
```

**Тип результата `outcome`** (только для `different`) — что именно предлагает банк:

| outcome | Клиент видит | Можно принять |
|---|---|---|
| `ALTERNATIVE_PRODUCT` | «Подобрали продукт» (клиент не выбирал) или «Предлагаем другой продукт» | да |
| `COUNTER_OFFER` | «Предлагаем другие условия» — та же программа, меньшая сумма | да |
| `MANUAL_REVIEW` | «Нужна дополнительная проверка» — оффера нет, ждём решения банка | нет |

**Решение банка поверх модели.** Модель не знает каталога, поэтому бэкенд:
- без выбранного продукта подбирает подходящий (сегмент, цель, сумма, срок, форма и возраст компании) с минимальной ставкой; не подошёл ни один — `declined` с причиной `NO_SUITABLE_PRODUCT`;
- если модель предлагает снизить сумму, а на неё выбранный продукт не выдаётся — подбирает другой продукт; не подошёл ни один — ручная проверка (`RECOMMENDED_AMOUNT_OUTSIDE_PRODUCTS`);
- считает условия `offer`: ставка внутри диапазона продукта по грейду (A — нижняя граница, E — верхняя), аннуитетный платёж.

**Действия клиента** (`actions` в ответе заявки): `accept` и `reject` — когда есть оффер (`confirmed` или `ALTERNATIVE_PRODUCT` / `COUNTER_OFFER`); `issue` и `reject` — после принятия; `retry` — после технической ошибки.

Промежуточный `pending` живёт от создания заявки до получения ответа ML (обычно доли секунды).

## 6. Полный путь пользователя

### Шаг 1. Регистрация

`POST /auth/register` с `username`, `email`, `password`, `password_confirm`. Пароль от 6 символов и совпадает с подтверждением, имя пользователя уникально. Возвращается `user_id`. Роль всегда `user`.

### Шаг 2. Вход

`POST /auth/login` с `email`, `password`. Возвращается `access_token`, `refresh_token`. Дальше все запросы с `Authorization: Bearer <access_token>`.

### Шаг 3. Заполнение профиля компании (один раз)

`PATCH /auth/me` с полями компании, финансов и кредитной истории. Пользователь заполняет это один раз, дальше данные переиспользуются во всех заявках. Дата регистрации и отчётный период не могут быть в будущем. Кредитную историю для скоринга банк всё равно берёт из БКИ (см. шаг 6).

Альтернатива: если профиль не заполнен, при создании первой заявки фронт отправляет эти данные вместе с заявкой, бэкенд сохраняет их в профиль.

### Шаг 4. Просмотр каталога продуктов (опционально)

`GET /products` — фронт показывает карточки. Пользователь либо выбирает конкретный продукт, либо не выбирает (тогда система сама подберёт по параметрам заявки).

### Шаг 5. Создание заявки

`POST /applications` с полями:

```json
{
  "requested_amount_rub": 1500000,
  "term_months": 24,
  "purpose": "equipment",
  "segment": "small",
  "product_type": "term_loan"
}
```

`product_type` опционален. Если он указан, продукт сверяется с каталогом (сегмент, цель, сумма, срок, форма и возраст компании): не подходит — `422` с понятным текстом. Если его нет — банк подбирает продукт сам (раздел 5). Поле `segment` принимается для совместимости, но сегмент считается по компании: микробизнес — до 15 сотрудников и до 120 млн ₽ выручки (209-ФЗ), иначе малый бизнес.

Заголовок `Idempotency-Key` (необязательный): повтор запроса с тем же ключом вернёт уже созданную заявку — двойной клик и сетевой повтор не создают дубль.

### Шаг 6. Обработка на бэкенде

1. Создать `ApplicationOrm` со статусом `pending`, скопировать snapshot всех данных из профиля
2. Записать событие `created`
3. **Обогащение**: вызвать мок-сервисы ЕГРЮЛ, ФНС, БКИ по ИНН. Сохранить ответы в `enriched_data`
4. Записать событие `enriched`. Если БКИ ответил — кредитная история в снимке заявки заменяется данными БКИ (банк знает историю действующего клиента сам); если нет — берётся история из профиля. К ней добавляются кредиты, которые банк уже выдал этому клиенту (статус `issued`): число, остаток (считаем, что погашений ещё не было) и ежемесячные платежи. Сводка по ним — в `enriched_data.bank_credits`
5. **Скоринг**: собрать `ScoreApplicationRequest` из снимка заявки, вызвать gRPC `ScoreApplication`
6. Получить ответ, применить правила банка (раздел 5): статус, `outcome`, `offer`, `explanation`. Сохранить `scoring_result`
7. Записать событие `scored` и событие `status_changed`
8. **Отправить WebSocket-уведомление** пользователю, у которого открыт канал
9. Вернуть `201` с полной информацией о заявке и её статусе

При ошибке ML статус меняется на `failed`, пишется событие `failed`, уходит WebSocket-уведомление, клиенту возвращается `502 / 504` с `application_id` сохранённой заявки. Повтор — `POST /applications/{id}/retry`: та же заявка, новая попытка шагов 3–9, событие `retry_started`; два повтора одновременно не запускаются.

### Шаг 7. Отображение результата

Frontend получает WebSocket-событие `status_changed`, обновляет UI. Показывает статус и тип результата (`outcome`), условия (`offer`), объяснение (`explanation`), главные факторы (`reason_codes`) и доступные действия (`actions`).

### Шаг 7а. Ручная проверка (сторона банка)

Если `outcome = MANUAL_REVIEW`, заявка попадает в очередь банка (`GET /admin/applications?outcome=MANUAL_REVIEW`). Сотрудник принимает решение: `POST /admin/applications/{id}/decision` с `approve` / `approve_with_conditions` (+ `recommended_amount_rub`) / `decline` и комментарием. Решение хранится в `bank_decision`, комментарий — в `explanation`, решение модели в `scoring_result` не меняется. Клиент получает итог по WebSocket.

### Шаг 7б. Принятие предложения и выдача

1. `POST /applications/{id}/accept` — «Принять предложение» → `accepted`, событие `offer_accepted`
2. `POST /applications/{id}/issue` — «Подтвердить условия и оформить» → `issued`, номер модельного договора (`contract_number`), событие `issued`. Выдача синтетическая: реальных проводок нет
3. `POST /applications/{id}/reject` — отказаться от предложения до оформления → `rejected_by_client`

Действия доступны только владельцу заявки; переход статуса проверяется и записывается одним `UPDATE`, поэтому повторный клик не оформит кредит дважды.

### Шаг 8. Просмотр заявки позже

`GET /applications/{id}` — детали. `GET /applications` — список заявок пользователя с курсорной пагинацией. `GET /applications/{id}/events` — история событий для восстановления таймлайна.

**Путь завершён.**

## 8. WebSocket

### Подключение

```
WS /ws/applications?token=<access_token>
```

JWT передаётся в query-параметре (стандарт для WebSocket — заголовки не работают в браузерном API). При невалидном или отозванном (после выхода из аккаунта) токене — закрытие с кодом 4401.

### Менеджер соединений

Хранит map `user_id → list[WebSocket]`. Позволяет одному пользователю держать несколько соединений (несколько вкладок). При отправке события рассылает всем каналам пользователя.

### Формат сообщений

Сервер → клиент:

```json
{
  "type": "status_changed",
  "application_id": "8a3f9c2e...",
  "status": "confirmed",
  "payload": {
    "outcome": null,
    "explanation": "Одобрено на запрошенных условиях: «Оборотный кредит», 3 000 000 ₽ на 12 мес. под 19.8% годовых, ...",
    "actions": ["accept", "reject"]
  },
  "created_at": "2026-03-15T10:00:01Z"
}
```

```json
{
  "type": "event",
  "application_id": "8a3f9c2e...",
  "event_type": "enriched",
  "payload": {"sources": ["egrul", "fns", "bki"]},
  "created_at": "2026-03-15T10:00:00Z"
}
```

Клиенту по WebSocket уходят только статус, тип результата, объяснение и доступные действия. Балл, PD, грейд и факторы модели — только в ответе `GET /applications/{id}`; банк видит всё в кабинете.

Клиент → сервер сообщений **не отправляет** (только ping/pong для keep-alive, если нужно).

### Гарантии

- Каждое изменение статуса гарантированно отправляется всем соединениям пользователя
- Если пользователь отключился — событие пишется в БД (`ApplicationEventOrm`), при переподключении фронт запрашивает `GET /applications/{id}/events` и восстанавливает состояние
- При статусе заявки, отличном от `pending`, повторная отправка `status_changed` не происходит (идемпотентность)

## 10. Интеграция с ML

МL-сервис уже существует и принимает gRPC `ScoreApplication`. Контракт не меняется.

**Что бэкенд отправляет в ML (из `ScoreApplicationRequest`):**
- `application_id` — сгенерированный бэкендом
- `application` — параметры заявки (product_type, requested_amount_rub, term_months, purpose, segment, submitted_at)
- `company` — реквизиты компании (inn, ogrn, legal_name, legal_form, okved, region, registration_date, employee_count)
- `financials` — финансовые показатели
- `credit_history` — кредитная история

Данные берутся из snapshot заявки (копия профиля на момент подачи). Кредитная история — из ответа БКИ, если он есть, плюс кредиты, уже выданные банком (см. раздел 6, шаг 4). После перезапуска ML gRPC-канал переподключается за несколько секунд (пауза переподключения ограничена 3 секундами).

**Что бэкенд получает от ML:**
- `score` (0–1000), `pd` (0–1), `risk_grade` (A–E)
- `reason_codes[]` — с готовыми русскими описаниями
- `decision.decision` — `approve` / `approve_with_conditions` / `manual_review` / `decline`
- `decision.reason_codes[]` — коды политики
- `decision.conditions[]` — например `{code: REDUCE_AMOUNT, recommended_amount_rub: 5000000}`
Ответ ML сохраняется в `scoring_result`. Объяснение для клиента (`explanation`) бэкенд собирает сам по шаблонам из кодов причин.

## 11. Что НЕ входит в MVP

Перечислено явно, чтобы не возникало вопросов при ревью:

- Пошаговый мастер заявки с черновиками — заявка создаётся одной формой
- Офферы с TTL (срок действия предложения)
- Загрузка документов по запросу банка, задачи на документы
- Настоящая электронная подпись и реальная выдача денег (выдача синтетическая — номер модельного договора)
- Сопровождение кредита (график платежей, остаток, просрочки)
- Множественные роли внутри компании (бухгалтер, наблюдатель, поручитель)
- Возможность привязать к одному пользователю несколько компаний
- CRUD продуктов через API (продукты заводятся seed при старте)

## 12. Технические требования к реализации

- Backend: FastAPI, SQLAlchemy async, PostgreSQL, gRPC-клиент к ML-сервису
- Все внешние интеграции — моковые, живут внутри backend под префиксом `/mock/`
- Все статусы меняются через единый сервис `ApplicationService` — никаких прямых `UPDATE` в роутерах
- Каждое изменение статуса пишет `ApplicationEventOrm` **и** отправляет WebSocket-сообщение **в одной транзакции с бизнес-операцией** (сначала БД, потом push; если push упал — событие всё равно в БД)
- Идемпотентность `POST /applications` через заголовок `Idempotency-Key` — сделано
- Все тесты (unit / integration / e2e) должны покрывать:
  - маппинг `decision → status` для всех 5 исходов
  - обогащение через 3 мока + обработку их ошибок
  - WebSocket: подключение, получение события, отключение
  - восстановление состояния после переподключения
  - каталог продуктов: список, детали, seed-идемпотентность
